# Statistical model code review

Reviewed on 12 September 2026 against commit `c167dd502f4012ff573c023d167fff8db89069d1`. The review covers correctness, clarity, conciseness, comments and use by students. This note records findings and proposed work. It does not change model code or fitted results.

The existing separation of settings, construction, fitting and reporting is useful. Further work should make those responsibilities easier to follow and remove places where the same statistical decision is described twice. Shorter code alone is a poor target. A short function that sends readers through several callbacks can be harder to understand than a longer, explicit calculation.

**Scope and evidence**

I inventoried all 420 Python files under `statistical_models`, including 276 model modules. Together they contain 105,201 physical lines, 8,061 comment tokens and 19,186 lines within module, class and function docstrings. These are inventory measures, not estimates of removable text. Docstrings attached to individual dataclass fields are not included in the docstring count.

I traced the ITT construction and reporting path, gain-factor construction and marginal summaries, DiD settings and prior reporting, mediation integration, shared execution stages, convergence checks, prior descriptions, metadata, publication decisions, child-level predictive validation and its refits. I also examined tests, report partials and the standalone pooling script. This is a broad review with deeper checks of selected paths, not a line-by-line mathematical audit of every model.

**Findings that warrant correction**

1. **P2. Prior displays can disagree with the fitted prior.** [The panel writer](../src/language_reading_predictors/statistical_models/priors.py#L1212) receives constructor names and calls each constructor with no arguments at line 1230. It therefore loses model-specific parameter values. I built the registered `lrp-rli-did-104` model through its current run plan. Its `arm_gap_t1` row correctly records `Normal(0, 1)`, but that row selects the `gamma_cross` panel, whose default constructor gives `Normal(0, 0.3)`. The report presents these panels as the model's priors in [the priors partial](../docs/models/_partials/_priors.qmd#L10). The same model's `sigma_child` row records the fitted `HalfNormal(1)`, but its rationale says `HalfNormal(0.5)` because [the shared constructor](../src/language_reading_predictors/statistical_models/factories/base.py#L113) fixes that number in text. These errors change the account of the assumptions, although the fitted distributions themselves are correct. Render from the actual prior specification, derive numerical descriptions from it, and distinguish priors with different parameter values even when they share a constructor. A regression check should compare the built distribution with the distribution passed to the plotter, including overrides and two different scales in the same model. The selected panels for the default `lrp-rli-did-001` model did not show a mismatch in the same probe.

2. **P2. The fallback for derived-quantity diagnostics discards chain identity and overstates its guarantee.** [The fallback](../src/language_reading_predictors/statistical_models/estimands.py#L93) removes non-finite values and treats the remaining samples as one chain. Its docstring calls the result a "single-chain lower bound". That bound does not hold. In a reproducible four-chain example, removing one draw changed bulk effective sample size from 6.16 to 9.57 and tail effective sample size from 34.72 to 61.96. The helper also reduced the estimated Monte Carlo error. The ordinary path preserves the original chains and is not affected. [The mediated-proportion summary](../src/language_reading_predictors/statistical_models/mediation.py#L147) can reach this fallback after removing undefined ratios. Reject an unrecoverable layout or mark the diagnostic unavailable. If diagnostics for a conditional quantity are needed, retain the chain and draw indices and define the conditional estimator explicitly. Effective sample-size estimation uses both within-chain dependence and differences between chains, as described in the [Stan reference manual](https://mc-stan.org/docs/reference-manual/analysis.html#estimation-of-effective-sample-size). This probe does not establish that a published headline passed a release check because of the fallback.

3. **P2. The pooled-moderation script no longer reads the models that estimate its target coefficient.** [The reader](../scripts/pooled_moderation.py#L48) searches `gf-001` through `gf-008` for `gamma_int_trt_own`. I resolved all eight current primary plans. Their only active interaction is age by ability. The treatment-by-baseline interaction is in `gf-201` through `gf-208`. A directory containing current primary fits therefore cannot supply the requested pool; older files that still contain the coefficient remain eligible because the reader does not check their model plan or convergence record. Decide whether this analysis is now historical or should be maintained. An update needs more than changing the model numbers. The `gf-205` baseline term is a binary off-floor indicator, whereas the graded models use a standardised baseline logit. Pooling those coefficients requires a stated common target. The module already acknowledges dependence between outcomes measured on the same children. Its use of posterior means and posterior standard deviations as if they were independent estimates and standard errors also needs justification before the workflow becomes a teaching example.

4. **P2. The import-cycle test constructs an incomplete dependency graph.** [The graph builder](../tests/statistical_models/test_module_architecture.py#L61) labels every nested file as `pipelines.<stem>`, including files under `factories` and `release`. The current 144 non-model module paths become 123 graph nodes. Some paths overwrite others, and import targets no longer match their source-node names. A temporary fixture containing `factories.a -> factories.b -> factories.a` produced no detected cycle. Naming nodes from their actual relative paths detected the cycle. The import reader also needs to resolve forms such as `from ...statistical_models import reporting`; these currently become an edge to `__init__`. Correct the graph representation and test it with deliberately cyclic and acyclic fixtures. This is a defect in the protection against future cycles, not evidence that the package currently fails to import.

The diagnostic example in finding 2 can be reproduced without fitting a model:

```python
import numpy as np
from language_reading_predictors.statistical_models.estimands import (
    derived_mc_diagnostics,

rng = np.random.default_rng(731)
```

The median claim deserves a worked counterexample. For three joint posterior draws with baseline logits `[-4, 0, 4]` and treatment coefficients `[1, 2, 3]`, the probability differences are approximately `[0.0294, 0.3808, 0.0171]`. Their median is `0.0294`. Evaluating the difference at the two median coefficients gives `0.3808`. A fixed multiplication from probability difference to items preserves the median. The calculation from several uncertain coefficients to an average probability difference is not a monotone transformation of one coefficient.

Keep comments that state array dimensions, units, reference populations, treatment coding, why a child must be held out as a group, why the guessing-floor link is required, and why a quantity lacks a causal interpretation. Keep licence notices and required authorship labels. These comments explain information the next line of Python cannot supply.

**A more approachable route for students**

The existing report reading guide explains Bayesian terms, and the generated model recipe explains the chosen design. Add a worked code walkthrough that connects them to one actual model. Start with `lrp-rli-itt-001`, then follow its settings, prepared arrays, factory, shared sampling steps and posterior summary. Give file links at each step. Use synthetic bounded scores so students can run it without the study data. Import the production functions so the example cannot quietly become a second implementation.

The walkthrough should show the following sequence:

1. State the question, what one row represents, and which children contribute to the estimate. Define the outcome count, maximum score, group indicator and baseline score.
2. Write the model equation beside the corresponding Python. Explain `eta` as the score's linear predictor on the logit scale, then show how it becomes a probability and an expected item count. Explain the Beta-Binomial concentration through its effect on score variation.
3. Draw from the prior and inspect simulated scores. Fit the posterior and explain what chain and draw dimensions mean. Examine computation and predicted-data checks separately. The [PyMC predictive-check tutorial](https://www.pymc.io/projects/docs/en/stable/learn/core_notebooks/posterior_predictive.html) provides a suitable companion exercise.
4. For each posterior draw, predict both assigned-arm conditions for the same covariate rows, take the difference and average over those rows. Only then calculate the median and equal-tailed interval. Include the small numerical counterexample above.
5. Introduce one complication at a time through a follow-on example: repeated observations within children, a binary off-floor outcome, or a mediator distribution. Show the assumption that changes as well as the extra code.

Use short names where they directly match a displayed equation. Use descriptive names for software operations and intermediate arrays, such as `baseline_logit`, `treatment_contribution` and `effect_draws`. Define ITT, ESS and other abbreviations on first use. State that passing computational checks does not establish correct causal assumptions. Present 89% coverage as the project's reporting choice, not as a statistical guarantee supplied by an unusual percentage.
