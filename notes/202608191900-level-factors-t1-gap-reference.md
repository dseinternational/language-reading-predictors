# Level-factors arm-by-time terms centred on the timepoint-1 gap (#552)

**Date:** 2026-08-19. **Decision (issue #552, confirmed by the author on 2026-08-19):** the `level_factors` family's per-timepoint arm coefficients are re-parameterised as a pre-randomisation **balance term plus changes** — `arm_gap_t1` (the covariate-adjusted immediate-minus-waitlist gap at t1) and `d_grp_time[t]` (the change in that gap at t2, t3 and t4), with the per-wave levels view `b_grp_time[t] = arm_gap_t1 + d_grp_time[t]` kept as a derived quantity — so that the randomised contrast is the **t2 change `d_grp_time[t2]`**, a difference-in-differences of adjusted levels, rather than the raw adjusted t2 gap `b_grp_time[1]`. This note records the implementation choices a future reader might question; the scientific rationale (the adjusted t1 gap is negative on every outcome because the immediate arm is older and higher on block design, and a levels model that conditions on nothing at baseline carries that chance imbalance into its t2 contrast) is in the issue and in `notes/202608180936-findings-04-level-factors.md`. The eleven `lrp-rli-lf-*` reporting refits are part of the post-review batch (#554) and had not been run when this note was written; nothing below is a result of record.

## What changed

- **Settings and plan.** `LevelFactorsModelSettings.arm_gap_reference` takes `"t1"` (the new default) or `"free"` (the pre-#552 free per-timepoint vector, retained as an explicit comparator). The resolved plan records `arm_gap_reference`, `focal_vector`, `focal_index` and `focal_term` (`d_grp_time[t2]` under `"t1"`, `b_grp_time[1]` under `"free"`, `None` for a pooled group term), and `config.json` / `model_recipe.md` carry them. Declaring `arm_gap_reference="t1"` with `group_by_time=False` is incoherent (a pooled coefficient has no t1 gap to centre on) and fails at resolution, before the output directory is reset or data are loaded.
- **Factory.** `arm_gap_t1` takes the cross-coupling prior (`Normal(0, 0.3)`, the `did` family's `arm_gap_t1` idiom — a nuisance balance quantity); `d_grp_time` (dims `post_phase` = `t2`, `t3`, `t4`) takes the outcome-tier treatment prior, so the prior sits on the randomised difference directly rather than on two raw gaps whose difference it would be; `b_grp_time` is a Deterministic with dims `phase`.
- **Consumers.** The items-scale t2 average marginal effect nets out `d_grp_time[t2]` and the group × ability interaction and adds back only `d_grp_time[t2]`; `arm_gap_t1` stays in both arms' linear predictor (it is not part of the effect). The key-findings builder, the release gate (`release.causal_term_for` reads the persisted plan's `focal_term`; a stored fit whose plan predates the field falls back to `b_grp_time[1]`, so pre-#552 reporting fits re-decide identically without a refit — verified on the stored `lf-001`, `-002` and `-005`), the level-family treatment-prior sweep, the τ forest (balance term beside the changes), the psense selection, the priors table and the report partial all read the plan. `factor_summary.csv` gains two roles beyond `causal` / `association`: `balance` (`arm_gap_t1`) and `levels_view` (the derived `b_grp_time[t]` rows, kept so the raw per-wave gaps — including the pre-#552 headline `b_grp_time[1]` — can still be read side by side with the new contrast). Vector elements are now labelled by coordinate value, so `factor_summary.csv` and `psense_summary.csv` name the same string (`d_grp_time[t2]`).

## Two things to know when reading the refits

1. **The t1 gap is partially pooled toward the later gaps.** Under the new parameterisation `arm_gap_t1` is informed by every wave, not only t1: the prior on each `d_grp_time[t]` shrinks the later gaps toward the t1 gap, so the posterior of `arm_gap_t1` is pulled toward the average adjusted gap across waves, and it carries a tighter prior (`Normal(0, 0.3)` rather than the free vector's outcome-tier `Normal(0, 0.5)`). The balance row will therefore **not** reproduce the stored free fit's `b_grp_time[0]` — on a `test`-preset fit of `lf-001` (word reading, 4 × 2000 draws, gate passed) `arm_gap_t1` was +0.03 [−0.37, +0.42] against the stored reporting fit's −0.17 [−0.58, +0.23]. Read `arm_gap_t1` as the model's balance nuisance term, never as a direct estimate of the t1 imbalance, and never as an effect.
2. **The new contrast is the trace-derived difference with the prior where it belongs.** The same `test` fit gave `d_grp_time[t2]` = +0.34 [+0.03, +0.66] (P(> 0) = 0.96; +2.3 words [+0.2, +4.3]) against the issue's trace-derived `b_grp_time[1] − b_grp_time[0]` of +0.42 [+0.07, +0.77] from the stored free fit — the same direction and overlapping intervals, a little smaller because the prior is now on the difference (the issue anticipated this: the derived difference under the free priors has an implied prior √2 wider). The acceptance check for the refit is agreement within prior-placement and Monte Carlo differences, not identity. The `test` fit is a pipeline check and is not a result; only the `reporting` refits are.

## Correction (2026-08-20)

The "Consumers" bullet above says `arm_gap_t1` "stays in both arms' linear predictor". That phrasing is wrong as written: the term multiplies `G`, so it appears only in the immediate arm's linear predictor. What the AME actually does (correctly) is leave it untouched — neither netted out of `eta0` nor added back — so it is present in both the with- and without-treatment predictions of each treated row, where it cancels from the logit contrast. The 2026-08-20 level-factors code review (finding 6, `notes/202608201500-level-factors-code-review.md`) corrected the same phrasing in the report partial, the `level_t2_marginal_effect` docstring and the test docstring; the computation was always right.
