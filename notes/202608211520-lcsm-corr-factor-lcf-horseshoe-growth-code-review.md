## Finding 1 (statistical reporting, major): gc-085's registered headline estimand never reaches any scientific output — the published report answers gc-069's question under gc-085's title

`lrp-rli-gc-085` is registered, titled and prose-documented as the age × ability interaction on growth rate ("do older-and-more-able children progress more?", #228 item 10), and the factory correctly builds `gamma_age` and `gamma_int` on the slope with both inputs centred. But `growth_association_summary` defaults to `coefs=("gamma", "delta", "beta", "loading")` (`reporting.py`), the pipeline calls it with no override (`pipelines/growth.py:200`) even though it computes `age_ability = plan.age_ability_interaction` a hundred lines earlier and uses it only for the diagnostic list, `_results_growth.qmd` has no interaction section, and `_kf_build_growth` reads only `gamma`. Verified on the stored reporting fit: `growth_association_summary.csv` contains only `beta`/`delta`/`gamma` rows, and the `key_findings.json` headline is "a 1-SD higher baseline non-verbal ability score was associated with a growth-rate change of **+0.15 logit units**" — that is `gamma`, the LRP69 estimand, not the interaction. The interaction posterior appears only in the collapsed technical convergence table. Two secondary consequences: the resolved run plan's estimand string is fixed regardless of `age_ability_interaction`, so gc-085's `model_recipe.md` and `config.json` — the #394 estimand-of-record — declare "gamma … is the headline Q5 association" on the same page whose title asks the interaction question (verified in the stored recipe); and `notes/202608181008-findings-17-growth.md` consequently reports gc-085 only via the same `gamma` number and never states any `gamma_int` posterior. The design note (`notes/202607141500-lrp228-age-ability-growth.md`) names `gamma_int_k` the headline and records no decision to exclude it from scientific reporting; no test asserts the interaction coefficients reach any published output, which is how this shipped through a reporting-tier release. **Recommendation:** pass the interaction coefficients into `growth_association_summary` when the plan declares them, add a `gamma_int` section to the partial, make `_kf_build_growth` prefer `gamma_int` when `resolved_run_plan.age_ability_interaction` is true, branch the estimand text, and update the 2026-08-18 findings note once the numbers exist; a test should pin that every plan-declared headline coefficient appears in the family summary CSV.

## Finding 2 (statistical reporting, major): the lcsm and corr_factor key-findings selectors let adjustment covariates displace the focal quantity, with wrong labels — live in six published boxes

Both families' key-findings builders pick "the clearest" row by `_kf_most_resolved_row` over a candidate set that mixes focal coefficients with adjustment covariates, then wrap the winner in a fixed sentence template. Three verified instances. (a) `_kf_build_lcsm` filters `coupling_summary.csv` to rows whose label contains `->` — which matches the age slope, the shared adjuster slopes and the lagged rows as well as the couplings — so `lrp-rli-lcsm-067`'s published box reads "The clearest longitudinal coupling was age -> reading change: **-0.15 logit units** … very strong evidence that a higher earlier level accompanies less later change". `d_age` is a precision covariate, not a coupling, and the fixed confidence template (about earlier _levels_) is wrong for it; the 2026-07-21 findings note had to re-frame the box by hand. (b) `_kf_build_corr_factor` ranks over every row of `structural_summary.csv` (factor slopes and covariates alike) under the label "structural slope": all four RLI fits publish "The clearest structural slope was beta age" (−0.32 to −0.37), and for `mm-002`/`mm-102` this displaces `beta_code` — the errors-in-variables code → word-reading slope the model exists to report (+0.35, 89% +0.10 to +0.61, P(>0) = 0.99; the module docstring's "documented PRIMARY mechanism") — because `beta_age`'s P(>0) = 0.001 is more resolved; the 2026-08-18 measurement note had to bypass the box to quote `beta_code`. (c) the lcsm window-1 highlight quotes the most-resolved outcome's randomised contrast without naming the outcome: `lrp-rli-lcsm-081` (focal outcome TE, whose docstring pre-specifies the consistency check against ITT-001/002 = TR/TE) publishes "+0.42 latent-logit units" — that is `itt_w1[W]` (word reading; TE is +0.29, TR +0.20) — and 091 publishes "+0.68", which is `itt_w1[L]`, not the focal W (+0.39). **Recommendation:** restrict the candidate sets to the plan's coupling/focal-slope names (both are recoverable from `resolved_run_plan`), name the outcome in the window-1 sentence (or pin it to the model's `outcome_symbol`), and vary the confidence templates by row type; the boxes regenerate without a refit via `scripts/regenerate_key_findings.py`.

## Finding 4 (statistical reporting, moderate): the horseshoe missing-data contract is misstated in both directions — the plan claims complete-case for the level fits that mean-impute, and the report claims imputation for the gain fits that are complete-case

`resolve_horseshoe_run_plan` records one uniform contract for every RLI port: `missing_data_assumption` = "Complete-case analysis over the model's required outcome, baseline, predictors and covariates …" and population "Available RLI rows with observed {outcome} and every declared predictor, composite component and covariate". That is true for the gain fits (`hs-001/003`: the span loader complete-cases every pre-score and covariate, so the factory's `nan_to_num` is a no-op) but false for the level fits (`hs-002/004`: `phase_mode="levels"` requires only group/age, and `_resolve_level_predictor` mean-imputes missing predictor levels — with the factory's own Group-C caveat that zero-imputation shrinks a patchy predictor's realised variance and pulls its coefficient toward the null). Verified in `lrp-rli-hs-002-reporting/config.json`. Conversely `_results_horseshoe.qmd` prints "_Missing values are mean-imputed._ …" for **every** RLI fit (the branch keys only on `study_id`), which is false for `hs-001/003`. (An earlier draft of this finding also attributed the family-wide imputation claim to `notes/202608181007-findings-16-horseshoe.md`; on re-checking, that note makes no missing-data claim, so only the plan strings and the partial carry the error.) A reader of the hs-002/004 recipe concludes the level ranking is robust to predictor missingness when it systematically disadvantages patchier predictors; a reader of hs-001/003 discounts the gain ranking for a bias it does not have. **Recommendation:** branch the plan's population/missing-data strings on the gain/level framing and the partial's paragraph on the recorded framing.

## Finding 5 (statistical reporting, moderate): the growth estimand-of-record mislabels `delta` as the association with "baseline LEVEL"

`delta` is the association with the level at the pooled-mean (mid-study) age: `age_std` is standardised over all child-wave cells, so the intercept sits at the panel mean, and the entry-level association is `delta + gamma·E[age_std at t1]` with `E[age_std at t1] < 0`. The repo states this correctly in `lrp_rli_gc_069.py` ("the _level at the sample-mean (mid-study) age_ … NOT at study entry"), in `_results_growth.qmd`, and in the RLM branch of the same resolver — but the RLI estimand string (`growth.py:385–386`), the factory docstring and the `growth_association_summary` docstring all say "baseline level", and the wrong wording is persisted into every RLI growth fit's `model_recipe.md` / `config.json` (verified in the stored gc-085 recipe). For a measure with a strong rate association the entry-level and mid-study associations can differ in sign, and the recipe is the plain-language account written for non-specialists. **Recommendation:** fix the three strings to the mid-study wording the module docstring already uses; the recipes can be rewritten in place for the stored fits without sampling.

## Finding 6 (missing pre-specified deliverable, moderate): the lcsm-081-vs-181 PSIS-LOO support criterion was never computed or recorded

`lrp_rli_lcsm_081.py` pre-specifies its support criterion as both couplings positive with P(g > 0) ≥ 0.9 **and** "this model is not LOO-worse than" the no-reverse-coupling comparator LRP-RLI-LCSM-181, and the #313-era design note lists the LOO comparison as a deliverable. No code computes it: `scripts/compare_statistical_models.py` has no lcsm branch, `output/statistical_models/comparison/` contains no lcsm artefact, and none of the findings notes quotes a LOO delta ± SE — they argue from coupling stability instead. The stored point elpd values (081: −1502.57 ± 19.54; 181: −1502.45 ± 19.37) differ by 0.12, which is meaningless without the paired pointwise SE, so half of the registered support criterion for the family's headline reverse-coupling hypothesis is unevaluated. The pairing itself is valid — 181 is 081 minus exactly the two reverse edges, over identical observed cells and likelihood — so a post-hoc `az.compare` over the stored traces can settle it without a refit. **Recommendation:** compute and record the paired comparison (a comparison-script branch or a small maintenance script), and state the result in the lcsm findings note either way.

## Finding 8 (functional, minor): falsy-`or` defaults silently replace declared-empty settings in lcsm and corr_factor resolution

`resolve_lcsm_run_plan` substitutes the full LRP67 default coupling set on `settings.couplings or (…)`, so an explicitly declared empty coupling set — the natural declaration for a couplings-free comparator — silently fits `g_L`/`g_E` anyway (the factory itself distinguishes `None` from empty correctly; only resolution collapses them). `resolve_corr_factor_run_plan` does the same with `structural_covariates or ("blocks",)` — a declared-unadjusted structural leg silently becomes blocks-adjusted, and `config.json` then records the substituted set, so the declaration is what is lost — and `from_legacy_extra` masks an explicitly-empty legacy `domains` the same way.
